## Origen operativo de logs dentro de la misma entrega

Captura de origen actual: en el host del operador, crear un directorio privado0700 y ejecutar `.venv/bin/python -m scripts.collect_access_resource_logs --output-directory DIRECTORIO`. El comando comprueba proyecto web-modelos para app/worker/Beat/Caddy/PostgreSQL/Redis, captura streams separados y conserva originales, fechas de creación, imágenes y huellas en un único archivo cifrado0600. No sobrescribe una captura anterior ni monta el socket de Docker en la web. Requiere la misma configuración de cifrado que el lector; nunca publicar el archivo ni tratarlo como descarga del titular.

La variable opcional `ACCESS_LOG_ORIGIN_BUNDLE` referencia ese archivo desde el proceso autorizado. La lectura del paquete ya auditada comprueba formato, permisos, propietario, hashes y captura posterior al corte del inventario. Solo muestra metadatos/referencias de candidatos asociados a identificadores explícitos del expediente, titular o fotos, y excluye eventos posteriores al corte. No muestra líneas originales, no incorpora logs automáticamente a la copia ni convierte ausencia de coincidencias en cobertura. Capturas antiguas/alteradas/inaccesibles bloquean la lectura configurada. El fichero necesita estar accesible con permisos privados para el UID del lector; no se incorpora un montaje ni cambio de runtime en esta etapa.

Los originales permiten continuar el tratamiento específico; siguen pendientes la asociación fiable y proyección/redacción de datos personales, orígenes históricos o contenedores eliminados, correo/host, cachés y diferencias en backups. Para estos últimos, aplicar el contraste de docs06: datos ya cubiertos no necesitan nuevas decisiones duplicadas, diferencias sí. El artefacto conserva partial=True y nunca es evidencia suficiente para habilitar cierre. No declarar una nueva entrega de utilidad: mantener todo dentro de CR09-END-ACCESS hasta prueba positiva de cierre/descarga.

Las decisiones de grupos del paquete permiten inclusión exacta, omisión motivada del grupo o redacción selectiva. Esta última usa `status=redacted` y `changes` por referencia original/campo; cada cambio lleva status omitted o redacted y motivo propio. Las redacciones textuales solo conservan fragmentos ordenados del original separados por `[redacted]`; no admiten texto nuevo ni sustituciones de números/objetos. Los campos no indicados se copian exactamente y el original permanece separado para la revisión independiente existente. No crear revisión/persistencia por cada campo ni volver a decidir datos ya cubiertos. Las exclusiones se explican en la copia sin incluir valores ocultos. Esto no entrega líneas de log aún sin adaptación ni elimina los pendientes de infraestructura.

Proyección admitida para registros operativos: JSON `subject-operation-v1`, sujeto explícito account/person/photo_blob vinculado exactamente al expediente/inventario, operación y resultado de listas cerradas, fecha consciente de zona y firma HMAC del servidor con dominio propio. `signed_subject_log_event` proporciona el formato de productor interno, sin endpoint público de firma; no está acreditada su emisión por proveedores actuales. Un JSON sin firma válida, con campos adicionales, versión desconocida o tipo no soportado sigue como candidato sin proyección; una coincidencia textual nunca autoriza entrega. Se proyectan solo fecha firmada, operación y resultado bajo el grupo adicional operations.LogEvent, sujeto a la misma decisión de inclusión/omisión/redacción y revisión independiente que el paquete. Las referencias privadas distinguen contenedor, stream y posición, conservando entradas repetidas; no se entregan línea original, firma o IDs técnicos del sujeto. Cambiar una captura después de aprobar el paquete invalida su origen incluso si se actualizan cifrado/hashes/firmas correctamente. Continúan todos los pendientes de cobertura operativa; esta adaptación no autoriza cierre por sí sola.

Correo local: el paquete contrasta exclusivamente la retención del backend locmem configurado y el email del titular mediante direcciones analizadas, incluidos nombres visibles. Referencias/huellas privadas cubren asunto, cuerpo, remitente, destinatarios, cabeceras, alternativas y adjuntos normales/MIME; solo se muestran contadores y situación de destinatarios compartidos, no valores ni enlaces/credenciales. Cambios de contenido cambian el origen del paquete. Quedan pendientes cuerpos/cabeceras/adjuntos y su proyección/redacción; console u otros backends mantienen pendiente propio y no se acreditan por esta lectura. Locmem solo representa el proceso local de pruebas, no historial de otros procesos ni transporte real. No equiparar prueba de backend local con entrega a un proveedor externo.

Proyección de correo de cuenta: el formato exacto emitido por send_token se asocia al titular mediante AccountToken en PostgreSQL y comprobación del hash del secreto. Se entrega como operations.Mail bajo la decisión/revisión del mismo paquete, con asunto, remitente, destinatario, finalidad, fecha de creación del token y cuerpo cuyo enlace de autenticación se oculta íntegramente; la copia explica esta exclusión. La fecha corresponde al token, no acredita envío/recepción. Caducidad o uso no borran el registro histórico ni autorizan autenticación. Mensajes compartidos, formatos desconocidos, cabeceras adicionales, adjuntos y alternativas mantienen pendiente de tratamiento; solo locmem está adaptado. Censo de recursos del operador dentro del mismo paquete: ACCESS_RESOURCE_ORIGIN_BUNDLE lee un archivo cifrado privado0600 (UID del proceso, archivo regular, sin seguir enlace final, lectura acotada). Esquema access-retained-resources-v1 liga request/inventory/source/cutoff/captured_at y dependencies (huellas de logs, correo, sesiones y colas). categories exige logs/mail/caches/backups/unlinked_records; cada categoría tiene reason, origins no vacío y pending explícito. Cada origen describe reference/method/evidence/records/records_digest. Registros tipados subject_kind/account o person, subject_id, created_at, content y source_reference; asociación/corte se verifican en servidor. Referencias de candidatos conocidos de logs/correo deben corresponder a su contenido original mediante huellas y contabilizarse todas. Fuente íntegra no significa censo verdadero/exhaustivo: el operador debe proporcionar fuentes/evidencias reales y el revisor independiente debe contrastarlas antes de aprobar el paquete exacto. No crear un censo vacío para eliminar pendientes del host, ni usar fixtures como acreditación externa. configuration_inspection describe evidencia del inventario de configuración, no una exclusión genérica de backups.
Los registros retenidos adicionales usan operations.RetainedResource y requieren omisión motivada o redacción explícita del campo content por registro dentro del grupo existente; no se copian automáticamente. resources.origin_digest enlaza la decisión al censo exacto, permanece privado y no se devuelve en JSON. Un censo faltante, pendiente o sin decisión ligada conserva infrastructure_content_accounting; operaciones externas/producción siguen pendientes. simulation se conserva expresamente en la copia pública. Las pruebas con censo sintético verifican este adaptador/flujo local, no exhaustividad de Docker/host/archivos reales. La aceptación operativa real permanece abierta.
