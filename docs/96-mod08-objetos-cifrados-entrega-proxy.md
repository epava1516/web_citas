# MOD-08 piezas 6/8: objetos privados y entrega por proxy

Diseño previo, 2026-10-10. Alcance: códec AEAD binario por bloques y repositorio S3 compatible privado; entrega efímera verificada con PostgreSQL y autorización por petición en Caddy. No altera documentos Fernet existentes ni sus llamadores; API explícita, adopción incremental en descarga.

## Cifrado y objetos

Cada objeto tiene DEK AES-256 aleatoria; bloques AES-GCM de hasta 1MiB con nonce prefijo aleatorio de cuatro bytes + contador de ocho bytes, exclusivo bajo su DEK. AAD liga versión, tamaño de bloque, prefijo y SHA256 del contexto de dominio (tipo/propietario/ID/version). La DEK se envuelve con KEK identificada y nonce aleatorio independiente. El encabezado y el frame final autenticados evitan truncamiento, reordenación, cambios de contexto y extensión. La rotación vuelve a envolver la DEK sin recifrar los bloques; verifica íntegramente su autenticación antes de rotar. El lector verifica el objeto completo en archivo temporal antes de devolver contenido: ningún prefijo se entrega ante una cola inválida.

Referencia compacta Fernet autenticada: versión, clave opaca aleatoria, digest SHA256 del ciphertext y longitud. No URLs públicas. PUT usa precondición de no existencia; bucket privado, sin versionado ni Object Lock para que borrado legal sea físico. DELETE debe confirmar ausencia API (HEAD404); no se infiere destrucción forense de bloques del motor ni de backups. Tombstones autenticados, fuera de PG, evitan resurrección por restaurar referencias o ciphertext viejo; preservar este ledger independiente al restaurar. Restauración conserva referencias y bytes exactos; inventario autoritativo de referencias y tombstones debe reconciliarse antes de exposición. No se acredita restauración PG desde un roundtrip S3.

## Entrega

AEAD cliente exige descifrado antes de servir JSON/ZIP/imágenes. Caddy no descifra estos objetos. Una operación ya validada prepara bytes íntegros en un directorio de entrega privada compartido (app RW, Caddy RO); PostgreSQL conserva grant ligado a la exportación y descarga auditada original. Archivo opaco, creación exclusiva, TTL máximo 30 segundos. URL firmada no sustituye autoridad fresca. Caddy `forward_auth` llama Django con secreto interno; GET revalida export/caso/sujeto/canal/proof/contenido y consume grant bajo lock; solo entonces copia el nombre opaco para `file_server`. HEAD no consume; replay/retry GET requiere otra descarga autorizada. El POST original cuenta una descarga; el grant registra un único consumo, sin duplicar RightsExportDownload.

La autoridad se decide por petición: una revocación posterior a la autorización no retira bytes ya abiertos por el proxy. No prometer autorización por bloque de red. La copia plaintext temporal se purga al vencer; al recuperar un backup se invalidan grants y se retiran todos los archivos de entrega antes de exposición. Nunca se respalda el directorio efímero. Endpoint interno rechaza acceso sin secreto de proxy; no expone rutas, errores de S3 ni credenciales. Cabeceras no-store/private, nosniff; no Range/reanudación para tokens de un uso.

## API y operación incremental

- `rights_object_content.seal_binary(content, export_id, kind, identifier)` y lector `unseal_binary` admiten referencias WMBlob1 y Fernet anterior; `image_bytes(row)` / `part_bytes(row)` derivan contexto del objeto propietario. Generadores actuales de acceso/portabilidad y fragmentos JSON usan estos helpers. `RIGHTS_OBJECT_STORAGE_ENABLED=1` activa nuevas escrituras S3; referencias existentes se leen físicamente incluso al desactivar nuevas escrituras. No migración masiva de datos.
- `rights_object_delivery.proxy_or_direct(export, recorded_download, response)` está integrado en las tres respuestas de descarga actual: opt-in POST303 hacia `/private-deliveries/<firma>`; desactivado, >8MiB o replay de un grant ya consumido conserva HTTP200 directo. Máximo un grantPG por descarga auditada; repetir POST antes de consumir devuelve el mismo grant y no prolonga su expiry. TokenGET un uso, HEAD/Range denegados sin contar/consumir. No se altera el endpoint canónico POST ni CSRF.
- `purge_export_objects(queryset)` destruye objetos S3 y copias plaintext antes de limpiar referencias SQL en expiración, supresión y reconciliación de recuperación. Purga no transaccional S3: si SQL revierte después del DELETE, referencias viejas quedan irrecuperables por tombstone; reintento es idempotente y seguro. Mantiene fuentes y auditoría.
- Beat10s ejecuta `purge_object_deliveries` y elimina huérfanos plaintext >30s; worker real probado. `purge_orphan_export_objects` barre abortosS3 >24h, sin borrar objetos referenciados; intervalo1h, recuperación deshabilitada. Generación de exportación está acotada a un tiempo inferior a esa gracia. No sustituye cuotas/censo global de almacenamiento N3.
- `verify_export_objects(export)` es obligatorio antes de confiar en un sello SQL si hay referencias externas. Puede omitir reconstrucción de la proyección; nunca comprobación física de esos objetos.
- Restauración: arrancar `RECOVERY_MODE=1`, mantener ledger de tombstones separado/autoritativo, restaurar DB/objetos vivos, ejecutar reconciliación del journal de recuperación, `invalidate_restored_deliveries()` y cambiar `RIGHTS_DELIVERY_GENERATION` en app/worker/Beat antes de exposición. Directorio efímero no se respalda. Roundtrip de objeto/tombstone no acredita restauración integral PostgreSQL.
