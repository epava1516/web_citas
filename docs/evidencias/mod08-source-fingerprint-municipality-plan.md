# MOD08: equivalencia y medición de la consulta de municipios

Preparado 2026-10-10 sobre integrado55a3da9. No hay medición SQL ni aceptación desde la inspección estática. El perfil parcial señaló dos llamadas source_fingerprint que dominaban etapas de unos10s; source_copy y validación Python eran minoritarias. Esto orienta el diagnóstico SQL, sin acreditar todavía causalidad del plan ni mejora temporal.

La consulta previa une cada municipio con revisiones del listing y usa un OR entre municipio directo y EXISTS de travel_areas correlacionado. La nueva selecciona primero IDs referidos por esas mismas revisiones: UNION de municipality_id directo y municipality_id del through unido a revisiones filtradas. Después hace semijoin con catalog_municipality. UNION deduplica referencias y cada municipio tiene PK única, por lo que no necesita DISTINCT exterior. Las referencias NULL nunca coinciden con una PK; listing NULL devuelve el conjunto vacío, igual que antes. Un municipio compartido con otros listings sigue incluido si este listing lo refiere. Filas exclusivamente ajenas siguen excluidas. No cambian tag,id,xmin:ctid, orden de agregación, familias de fuente, contador, hash, ramas sinlisting/cuenta ni ninguna autoridad.

Regresión pendiente PostgreSQL: tests/test_rights_source_fingerprint.py completo. El nuevo caso compara conjuntos exactos de parejas(id,version), triples(tag,id,version), hashSHA256 y count frente al SQL previo en la misma transacción. Cubre referencias repetidas, directo también travel, NULL con/sin travel, varios revision, municipios compartidos, foreign/unused, listing NULL, rama cuenta intacta y UPDATE de municipio referido/ajeno. Mantiene las pruebas previas de todas las familias, mutación INSERT/UPDATE/DELETE, deriva del llamador y escritura concurrente. No se ejecutó PG en el worktree: raíz coordina N2 tras integración.
