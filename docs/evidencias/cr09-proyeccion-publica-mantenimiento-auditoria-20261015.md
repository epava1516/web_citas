## Cadena transaccional y límites

Los triggers AFTER por sentencia cubren INSERT/UPDATE/DELETE con filas anteriores/nuevas y TRUNCATE (`0015_publication_state.py:108-131`); Listing y Revision están cubiertas (`:37-38`). El marcador hace upsert con nueva generación (`:96-104`). Por ello save, setters que escriben, QuerySet.update, bulk_update/bulk_create y SQL ordinario sobre esas tablas invalidan sin depender de señales Python. No se extiende esta afirmación a triggers deshabilitados, restauraciones especiales ni manipulación directa de PublicationState; son límites operativos, no fallos observados.

`refresh` bloquea las marcas con SKIP LOCKED, protege referencias con KEY SHARE NOWAIT y elimina sólo generaciones reclamadas (`publication_state.py:179-217`). En READ COMMITTED sus consultas pueden ver snapshots distintos: una escritura de dependencia posterior a la reclamación queda esperando el upsert del dirty hasta que termine el refresher; al confirmar el escritor, debe quedar otra marca. La copia antigua puede publicarse antes que ese escritor, pero todavía corresponde al dominio confirmado anterior. Si el escritor confirmó antes de reclamar, la lectura posterior debe verlo. El test existente de Person (`tests/test_publication_state.py:246-285`) ejercita una de estas secuencias; no demuestra todavía copia coherente de fechas/vector/cambio de revisión.

No afirmar una garantía universal a partir de ese razonamiento: hay múltiples lecturas dentro de PublicationContext (`public_validation.py:403-437`) y dependencias indirectas. La candidata debe demostrar que ninguna modificación relevante puede confirmar sin marcar el mismo listing y que no se mezcla vector de una revisión nueva con revision_id viejo. Copiar en una consulta tardía independiente puede mezclar dos versiones dentro de READ COMMITTED si se reutiliza mal la identidad; exigir la misma fila hidratada evita introducir ese riesgo específico. Una mutación concurrente que espera dirty debe dejar la generación posterior incluso si el refresher elimina la anterior.

El lector propio abre REPEATABLE READ READ ONLY (`publication_state.py:348-363`). Dirty, cobertura, count, selección e hidratación comparten snapshot; una confirmación posterior no los invalida retroactivamente. Un lector heredado READ COMMITTED no lo tiene: comprobar limpio y luego leer puede cruzar una confirmación. Ya se conserva el predicado original fuera del snapshot propio (`:412-415`; test de revisión obsoleta `test_publication_state.py:451-501`). No activar allí la proyección.
