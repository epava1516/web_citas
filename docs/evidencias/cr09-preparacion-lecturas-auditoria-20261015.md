## Propiedad temporal y errores

`public_validation.py:201` valida la pertenencia del wrapper al hilo, captura la conexión física y guarda ambos atributos antes de cambiarlos. El `finally` (`:209`) restaura fábrica y umbral, también tras error de SQL o anidamiento síncrono. La conexión ya existe porque `read_publication_values` ha entrado en `atomic` y ha ejecutado SQL antes (`:225`). El anidamiento restaura primero el estado del ámbito exterior; no fuerza valores globales de fábrica o umbral. Los tests `test_publication_prepared_binding.py:19` y `:37` describen esta propiedad con dobles; `test_publication_page_planning_scope.py:20` añade restauración de opciones y GUC ante fallo SQL real cuando lo ejecuta el principal.

El ámbito no es un bloqueo exclusivo de conexión. `validate_thread_sharing` no impide que un consumidor habilitado expresamente para compartir el wrapper, o alguien con la conexión raw, intercale cursores. Además, todo cursor creado durante `list(query)` usa temporalmente esta fábrica: incluye prefetch (`PublicationContext`, `public_validation.py:408`), y podría incluir consultas añadidas por hooks. Contraejemplo condicionado: si un hook futuro ejecuta dentro de esa evaluación una orden que sólo admite interpolación cliente, el nuevo enlace servidor podría rechazarla. No se ha encontrado tal orden en las fuentes actuales; no se presenta como defecto existente. El ámbito de fábrica no constituye por sí mismo una lista blanca SQL de SELECT.

La restauración GUC de éxito es explícita (`public_validation.py:237`); ante error no se intenta consultar una transacción rota y el `atomic` revierte el savepoint o la transacción. Esto conserva el estado previo del llamador. Un cierre/reemplazo manual de la conexión dentro de la evaluación dejaría al `finally` restaurando el objeto raw capturado, no una conexión nueva. No es comportamiento encontrado en la ruta actual; una reconexión transparente dentro de una transacción fallida tampoco es una garantía de este helper.

## Frescura, vida de planes y límites de despliegue

`publication_state.py:348` abre REPEATABLE READ READ ONLY cuando controla la transacción. Selección, guardia y prefetch ven ese snapshot; «fresco» significa ese snapshot, no observar una revocación confirmada después de iniciarlo. En transacciones heredadas se conserva el aislamiento del llamador y se desactiva el atajo de población hermana (`:412`). Preparar no añade una caché de elegibilidad: siguen las comprobaciones dirty/versión/desconocidos (`:372`), los límites que devuelven `None` (`:373`, `:384`) y la guardia nativa de cada fila (`:427`). Los catálogos se construyen fuera del ámbito de fábrica, pero dentro de la transacción exterior de `state_page` (`public_validation.py:466`).

Una transacción heredada READ COMMITTED puede ver cambios entre sentencias; esta limitación ya existía en la lectura cliente y no la soluciona preparar. No se afirma equivalencia ante cualquier escritura concurrente entre sentencias. El test de revocación posterior a preparar (`test_publication_prepared_binding.py:97`) cubre revocación entre peticiones y comparación de contenido/conteo; no es una prueba de toda intercalación concurrente.

Restaurar `prepare_threshold=None` no vacía los planes preparados: el setter instalado sólo asigna el umbral (`psycopg/_connection_base.py:405`). Esta persistencia es intencionada para amortizar preparación. Los planes pertenecen a la sesión física; cerrar/reconectar pierde esa amortización, sin justificar reutilizar resultados. `config/settings.py:59` configura PostgreSQL directo con `CONN_MAX_AGE=60` (`:67`) y no declara pool. Django desactiva preparación por defecto precisamente por compatibilidad con poolers (`base.py:296`). Este helper la reactiva temporalmente: la compatibilidad con un pooler externo por transacción no queda acreditada por esta nota ni por una prueba con conexión directa. No se ha establecido que exista tal pooler en el despliegue actual; no debe inventarse un fallo de producción.
